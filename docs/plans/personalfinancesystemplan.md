# แพลนระบบจัดการบัญชีส่วนตัว (Personal Finance Management System)

> เอกสารนี้แยกเป็น 2 ส่วนหลัก: **(1) ความต้องการของระบบ (Requirements)** ที่สรุปมาจากที่ให้มา และ **(2) ประเด็นทางเทคนิค/ข้อสมมติฐาน/คำถามที่ต้องตัดสินใจ** ก่อนส่งให้ AI ไปพัฒนาต่อ

---

## ส่วนที่ 1: Requirements (ความต้องการของระบบ)

### 1.1 User Management
- ระบบรองรับหลาย User (ระดับครอบครัว) โดยแยกข้อมูลรายบุคคล
- 1 User สามารถมีได้หลายบัญชีธนาคาร และหลายอีเมล
- แต่ละ User กำหนดเองได้ว่าจะให้ระบบตรวจอีเมลใดบ้าง (เพิ่มได้มากกว่า 1)

### 1.2 Onboarding (ผู้ใช้ใหม่)
> ปรับปรุง 2026-08-27 — ดู `docs/adr/0001-statement-pdf-ingestion.md`
- **ก่อนเริ่ม ผู้ใช้ต้องไปขอ statement ย้อนหลังจากธนาคาร ให้ส่งเข้าอีเมลของตัวเองก่อน**
  ระบบย้อนอ่านเองไม่ได้ เพราะแหล่งข้อมูลคือไฟล์ statement ไม่ใช่อีเมลแจ้งเตือนรายธุรกรรม
- หลังสมัครสมาชิก ผู้ใช้กรอก: ธนาคาร + ชื่อเล่น + กล่องอีเมลที่ให้ระบบอ่าน + เลขที่บัญชี + รหัสผ่านเปิดไฟล์ statement
- เมื่อบันทึก ระบบจะค้นอีเมล statement ที่ผู้ใช้ขอไว้ (หัวข้อตามที่แอดมินกำหนด) แล้ว import เป็นข้อมูลตั้งต้น (backfill)
- ช่วงข้อมูลตั้งต้นเท่ากับช่วงที่ statement ที่ผู้ใช้ขอครอบคลุม ไม่ใช่ "ตั้งแต่ต้นปี" เสมอไป

### 1.3 บันทึกรายรับ-รายจ่าย
> ปรับปรุง 2026-08-27 — ดู `docs/adr/0001-statement-pdf-ingestion.md`
- ดึงข้อมูลธุรกรรมจาก **ไฟล์ statement PDF รายเดือน** ที่ธนาคารส่งเข้าอีเมล (ไฟล์เข้ารหัสรหัสผ่าน ผู้ใช้เป็นคนกรอกรหัสไว้)
- **ไม่ใช้อีเมลแจ้งเตือนรายธุรกรรมแล้ว** เพราะ K PLUS ไม่ส่งอีเมลแจ้ง "เงินเข้า" เลย → ledger จะเห็นแต่ขาจ่าย ทำให้ข้อ 1.5 และ 1.6 เป็นไปไม่ได้
- บันทึกเงินเข้า-ออกเป็นรายการรายรับ/รายจ่าย พร้อมยอดคงเหลือต่อบรรทัด
- **ข้อแลกเปลี่ยน:** ข้อมูลไม่สดแบบเกือบ real-time อีกต่อไป ledger ช้าได้ถึง ~35 วัน (ยอมรับแล้ว)
- launch รองรับ KBank ธนาคารเดียวก่อน (แต่ละธนาคารฟอร์ม statement ไม่เหมือนกัน ต้อง dev แยก)

### 1.4 ตรวจจับรายการโอนเงินภายใน (Internal Transfer Detection)
- ต้องแยกให้ได้ว่ารายการที่เกิดขึ้น เป็น "รายรับ-รายจ่ายจริง" หรือ "การโยกเงินระหว่างบัญชีของตัวเอง" (เช่น โอนจากบัญชี A ไป B ที่เป็นเจ้าของเดียวกัน) เพื่อไม่ให้นับซ้ำเป็นรายรับ/รายจ่าย

### 1.5 รายงานสรุป (Reporting)
- สรุปแบบ รายวัน / รายสัปดาห์ / รายเดือน / ช่วงเดือนที่กำหนดเอง / รายปี

### 1.6 สรุปภาษีประจำปี
- สามารถสรุปรายได้ทั้งปี เพื่อใช้ประกอบการยื่นภาษี

### 1.7 จัดเก็บ Tax Invoice (ใบกำกับภาษี/ใบลดหย่อน)
- ระบบเข้าไปอ่านอีเมลที่ผู้ใช้กำหนดไว้ เพื่อดึงข้อมูล/ไฟล์ Tax Invoice มาเก็บ
- หมายเหตุ: ส่วนนี้ **ทำแบบอัตโนมัติเต็มรูปแบบไม่ได้** เพราะไม่มีรายชื่อผู้ส่งตายตัว ต้องให้ผู้ใช้เป็นคนกำหนด/เลือกเองว่าอีเมลไหนคือ Tax Invoice

### 1.8 ระบบแอดมิน (Admin/Central Management)
- แอดมินกำหนดได้ว่าจะรับอีเมลจากผู้ส่ง (sender) รายใดบ้าง (whitelist)
- แอดมินเพิ่ม/จัดการรายชื่อธนาคารที่ระบบรองรับได้ (เพิ่มธนาคารใหม่ในอนาคต)

## ส่วนที่ 2: ประเด็นทางเทคนิค / ข้อสมมติฐาน / สิ่งที่ต้องตัดสินใจก่อนสั่งให้ AI สร้าง

### 2.1 สถาปัตยกรรมข้อมูล (ที่ควรมีตามความต้องการข้างต้น)
- `User` — ผู้ใช้งาน
- `EmailAccount` — อีเมลที่ User ผูกไว้ (many-to-one กับ User)
- `BankAccount` — บัญชีธนาคารของ User (many-to-one กับ User, ผูกกับ Bank)
- `Bank` — รายชื่อธนาคาร/แอป ที่แอดมินดูแล (ชื่อ, รูปแบบอีเมล/sender ที่ยอมรับ, template สำหรับ parse)
- `AllowedSender` — รายชื่อผู้ส่งที่แอดมิน whitelist ไว้ (ผูกกับ Bank)
- `Transaction` — รายการเข้า/ออก (จำนวนเงิน, วันเวลา, บัญชีต้นทาง, คู่กรณี, หมวดหมู่, ที่มา/อีเมลต้นฉบับอ้างอิง, flag ว่าเป็นการโยกเงินภายในหรือไม่)
- `TransferMatch` — คู่รายการที่ระบบจับคู่ว่าเป็นการโอนภายใน (debit-credit matching)
- `TaxInvoiceRecord` — ข้อมูล/ไฟล์ใบกำกับภาษีที่ผู้ใช้เลือกเก็บ (ผูกกับอีเมลต้นฉบับ)
- `Category` — หมวดหมู่รายรับ/รายจ่าย

### 2.2 กลไกดึงอีเมล (Email Ingestion) — ต้องตัดสินใจ
- **ผู้ให้บริการอีเมล: Gmail เท่านั้น (เฟสแรก)** → เชื่อมต่อผ่าน **Gmail API + OAuth 2.0** (ไม่ใช้ IMAP/App Password) รองรับ multiple Gmail accounts ต่อ User
- แต่ละธนาคารมีรูปแบบอีเมลไม่เหมือนกัน → ต้องมี "parser/template" แยกตามธนาคาร/sender และต้องดูแลเมื่อธนาคารเปลี่ยนฟอร์แมตอีเมล
- การ backfill ย้อนหลังตั้งแต่ต้นปี อาจมีปริมาณอีเมลมาก ต้องคิดเรื่อง rate limit และ background job/queue

### 2.3 ตรรกะจับคู่ Internal Transfer
- ต้องกำหนดเกณฑ์การจับคู่ เช่น ช่วงเวลา (time window), จำนวนเงินตรงกัน, บัญชีทั้งคู่เป็นของ User เดียวกัน — ควรให้ผู้ใช้ยืนยัน/แก้ไขได้กรณีจับคู่ผิด (manual override)

### 2.4 ความปลอดภัยและความเป็นส่วนตัว
- ข้อมูลอีเมล/บัญชีธนาคารเป็นข้อมูลอ่อนไหว: ต้องเข้ารหัส token การเชื่อมต่ออีเมล และแยกสิทธิ์การเข้าถึงข้อมูลรายบุคคลอย่างเคร่งครัด แม้จะเป็นระบบใช้ในครอบครัวเดียวกัน
- ควรมี audit log การเข้าถึง/แก้ไขข้อมูล

### 2.5 ขอบเขตและ Scope ที่ตัดสินใจแล้ว
- **Phase 1**: เว็บแอป (Responsive) — ใช้งานได้ทั้งจอเดสก์ท็อปและมือถือผ่านเบราว์เซอร์
- **Phase 2** (ในอนาคต): แอปมือถือ (native/hybrid — ให้ AI แนะนำแนวทางตอนถึงเฟสนั้น)
- **Frontend**: React (กำหนดตายตัว)
- **Backend/Database/Infra**: ให้ AI เป็นผู้แนะนำและตัดสินใจ โดยพิจารณาว่าจะ deploy ลง **VPS Cloud ที่มีอยู่แล้ว** เป็นหลัก
- **ภาษา UI/สกุลเงิน**: ภาษาไทย, สกุลเงิน THB (เฟสแรก)
- **การแจ้งเตือน**: ยังไม่ต้องการ (ไม่ต้องทำ LINE Notify หรือ notification channel อื่นในเฟสแรก)
- **การเก็บไฟล์ต้นฉบับอีเมล/ใบกำกับภาษี และ backup**: ให้ AI แนะนำแนวทาง (retention period, storage strategy, backup schedule) แล้วเสนอมาให้พิจารณาก่อนตัดสินใจ

## ส่วนที่ 3: Design Guideline (UI)

### 3.1 แนวทางภาพรวม
- สไตล์: **Modern Minimal**
- ธีม: รองรับทั้ง **Light mode (ค่าเริ่มต้น) และ Dark mode**
- Palette อ้างอิงจากสีตัวละคร **Hyacine (Honkai: Star Rail)**

### 3.2 Design Tokens

```css
--color-bg: oklch(98.21% 0.0069 304.24);
--color-surface: oklch(100% 0 0);
--color-primary: oklch(55.49% 0.2143 14.10);
--color-primary-hover: oklch(49% 0.19 14.10);
--color-petal: oklch(83.75% 0.0745 1.77);
--color-lavender: oklch(87.40% 0.0512 303.02);
--color-mint: oklch(90.29% 0.0440 187.54);
--color-honey: oklch(89.77% 0.0712 80.61);
--color-ink: oklch(27% 0.055 14.10);
--color-muted: oklch(47% 0.035 304.24);
--color-border: oklch(89% 0.025 304.24);
```

### 3.3 กติกาการใช้สี (Semantic Rules)
- **Hyacinth Crimson** (`--color-primary`) → primary action, focus state, headings, สถานะสำคัญ/error/หยุดทำงาน
- **Aqua Mint** (`--color-mint`) → สถานะปกติ/active/success (เช่น sync สำเร็จ, ยอดเข้า)
- **Honey** (`--color-honey`) → คำเตือน (warning) เท่านั้น
- **Petal / Lavender** → สีรอง/พื้นผิวตกแต่ง (accent, badge, background เบา ๆ) ไม่ใช้แทนความหมายสถานะ
- สีต้อง**คู่กับ text หรือ icon เสมอ** ห้ามสื่อความหมายด้วยสีล้วน (accessibility)
- `--color-ink` / `--color-muted` สำหรับข้อความหลัก/รอง, `--color-border` สำหรับเส้นขอบ/แบ่งพื้นที่

### 3.4 Typography
- แนวฟอนต์: **Pixel / 8-bit style** ใช้กับปุ่ม (buttons) และคำอธิบาย/label ต่างๆ เพื่อสร้าง character ให้ UI
- ต้องเป็นฟอนต์ที่**รองรับภาษาไทย** (ฟอนต์ pixel ที่รองรับไทยมีจำกัด — AI ควรเลือกจากตัวเลือกเช่น "Pixel Thai", "Pixelify Sans" (เฉพาะ Latin), หรือ custom/self-hosted font ที่ทำ glyph ไทยแบบ pixel — ให้ AI ช่วยเลือก/เสนอตัวเลือกที่ใช้งานได้จริงและ license ถูกต้อง)
- เนื้อหาหลัก/ตัวเลขจำนวนเงิน (เช่น ตัวเลขในรายงาน ตาราง) แนะนำใช้ฟอนต์อ่านง่ายทั่วไป (ไม่ใช่ pixel) เพื่อความชัดเจนของตัวเลขทางการเงิน — ให้ AI เสนอ font pairing ระหว่าง pixel (accent) กับฟอนต์อ่านง่าย (body/ตัวเลข)
- Scale: ใช้ตามมาตรฐานทั่วไป (type scale แบบ modular เช่น 12/14/16/20/24/32px) ให้ AI กำหนดตาม pattern มาตรฐาน

### 3.5 Spacing & Radius
- ใช้ตามมาตรฐานทั่วไป (standard scale) เช่น spacing ฐาน 4px/8px (4, 8, 12, 16, 24, 32, 48...) และ border-radius ระดับกลาง (ไม่ full-round, ไม่เหลี่ยมจัด) — ให้ AI กำหนดค่าที่เป็นมาตรฐานอุตสาหกรรม

### 3.6 Dark Mode
- **ต้องรองรับ Dark Mode**
- หมายเหตุ: ค่าสี dark mode tokens ยังไม่ได้กำหนดมา (มีแต่ light mode ด้านบน) → ให้ AI สร้างชุดสี dark mode ที่คง semantic เดิม (primary/mint/honey ทำหน้าที่เหมือนเดิม) โดยปรับ lightness/contrast ให้เหมาะกับพื้นหลังมืด และผ่านเกณฑ์ accessibility contrast (WCAG AA อย่างน้อย)

### 3.7 Icon Set
- ใช้ **Lucide** icons ทั้งระบบ
